# 体素校园 BGM 分段请求与取消修复 · 2026-10-30

用户观察到 BGM 首播较晚，网络面板中同一首 Opus 在几十秒后又出现请求。本轮以 `0cee85c7d9da3e08b68342f882f9a88e078ae811` 为基线，检查实际音频、公开生产响应和播放器生命周期。本轮只合并修复，没有再次部署树莓派。

## 已确认的现象

生产 Chrome 的只读播放观察中，点击启程后 223ms 发生 `playing`；此时白昼曲目只缓冲了 `[0,56.315]` 和 `[93.859,106.5065]` 秒，中间仍有空档。约在点击后 33.989 秒，浏览器发出补段请求，该次请求耗时约39ms；抵达时音乐已播放约33.808秒。这个浏览器缓存未清空，223ms不能作为空缓存首播性能承诺。

因此，截图上晚出现的 `206` 请求本身不是一个持续几十秒的慢请求，也不能推断应用等待整首下载才播放。Chromium 会根据播放位置、缓冲高低水位暂停或继续媒体读取；Ogg/Opus 还可能读取尾部来确定时长。参考 [Chromium 媒体缓冲说明](https://www.chromium.org/audio-video/) 和 [Ogg Opus 格式规范](https://www.rfc-editor.org/rfc/rfc7845.html#section-4.6)。本轮首段与尾段公网 Range 探针均返回正确的 `206`、`audio/ogg`、`Content-Range` 和原始字节，未发现服务端 Range 损坏。

三份原音乐的前段另有较安静的引子：以-50dB、持续至少0.2秒为阈值，清晨/黄昏约0.351秒、白昼约2.143秒、月夜约1.763秒。这个阈值不等于绝对静音；应用首播还保留1.2秒淡入。未裁剪、重编码或替换音乐。

## 复现并修正的问题

在尚未返回响应头的慢网夹具中，点击启程后立即切换月夜，旧实现同时保留两个未就绪、`paused=false` 的播放器及两条请求。请求编号只会忽略旧 Promise 的结果，没有取消旧网络传输。旧曲目此时尚未参与输出，继续加载会与当前选择竞争带宽。

`CampusAudio` 现在标记等待中的播放请求。切换或静音时，对已失效且尚未参与输出的曲目执行 `pause()`、移除 `src` 和 `load()`，实际中止请求与旧播放 Promise；正常取消不会触发重试错误。重新选择该曲目时只恢复原URL，复用原播放器和 MediaElementSource，仍最多三个播放器。已经开始输出的曲目继续保留到交叉淡化结束。

不以预下载三首、等待 `canplaythrough` 或完整解码替代流式播放。页面没有交互意图时仍不下载音乐，主动静音后再次启程仍保持关闭。
